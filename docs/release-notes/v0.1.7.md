## English

### What changed since 0.1.6

**Storage goes through EF Core again**
- The database is read and written through EF Core (as in 0.1.0–0.1.2) instead of hand-written SQL; it is still encrypted with
  SQLite3 Multiple Ciphers.
- **No backward compatibility:** files of 0.1.0–0.1.6 are not upgraded, and there is no code that recognises them: no schema version is
  written or checked. A new data folder gets its tables from EF Core; a database of another layout is opened as it is and fails where
  it does not fit (an error, not a special screen). Remove the old data folder by hand to start fresh. Restoring checks only the backup
  file format (`TMCBAK03`): a format 02 backup of 0.1.1–0.1.5 is refused with a plain message ("this version loads only the backups it
  made itself"; the technical reason goes to the log), not as a wrong password. A backup taken with an earlier 0.1.7 build still
  restores: the `schema-version` settings row it carries is left alone and does no harm.
- The first start: going **Back** clears the backup file and password typed on the other page (the two pages share the password field),
  the restore page explains itself once (behind its "?"), and a restore shows its step under the form: opening the backup, checking the
  contents, setting up the database, writing the images. A restored profile that uses the local meaning check (MiniLM) asks to install
  it at the first concept run (the tools folder is not in a backup) instead of failing.

**Deleting for good no longer makes the file smaller (no VACUUM)**
- 0.1.6 ran `VACUUM` after a permanent delete and on every backup copy. VACUUM is an SQL statement with no EF Core counterpart, so 0.1.7
  does not run it.
- What is deleted is still unreadable: the SQLite build overwrites deleted rows **and the pages they free** with zeros (secure delete; the
  app checks it every time a database comes in and refuses a build without it). Tests look for deleted text in the raw file — after a
  permanent delete and in a backup copy without the parts that were not chosen — and find none.
- What changes: the database file and backups do not shrink after a delete. The zeroed pages stay in the file (and in a backup's
  database copy) until SQLite reuses them for new data, so a backup can be larger than the same content made by 0.1.6. Whether this is
  acceptable is an **open decision**; until it is made, it is the behaviour of this version.

**Long answers stream; the video code has room for its thinking**
- Video code answers were cut off at 32 000 output tokens: the model's adaptive thinking takes from the same budget (two Opus 5.5 answers,
  effort high, stopped after about 5 minutes and about 0.65 $ each). The budget is now 64 000 tokens, or the model's own limit when that
  is smaller, for the code and for its single repair. The estimate's high end counts this whole budget (it counted 14 000 before).
- Answers are read while they stream: Anthropic always (it already asked for a stream, but the app waited for the whole body under one
  15-minute limit), the OpenAI-compatible providers for the long calls (concepts, video code; with `stream_options.include_usage`, sent
  once more without it when a provider rejects it). A streamed answer must start within 15 minutes; then it may run up to 60 minutes and
  stops only when nothing arrives for 3 minutes. The log line of a streamed call has its time, size, first-line time and request id; a
  stream that breaks carries the tokens already billed into the cost.
- A cut-off video code says what happened: "the video code was cut off because it was too long; spent X $" (it said "the complete
  concepts before the cut were kept", which is the concept page's text).

**Fixes in video making and the estimates**
- A narration model that could not be prepared (not installed, wrong language) stopped the queue with an error after the warning; the
  video is made silent now, as the warning says.
- "Sample images" chosen for a profile that has none made a video without images and said nothing; now it says so (activity line and a
  note in the video's details).
- The concept estimate with the meaning check left out the earlier concepts it embeds first (up to 300 per batch of 20 the first time,
  or after the model changed). They are in the estimate now, and the page says how many; with the local model it costs nothing but takes a
  while.
- The details of a video whose narration skipped words showed a text key instead of the note.

**What a failed video paid, and clearer cost details**
- A video that fails keeps what it paid until then: the queue row says "spent because of the failure: X $" (added up over the failed
  tries of that item, also after a restart), and the month's spending has a "failed videos" part (it used to leave this money out).
- The cost details of a made video follow the work: the concept's share of its generation run (the run's cost ÷ the concepts it kept,
  for example 0.11 $ for 5 concepts → 0.022 $), the narration text and scene split (on this computer, free), the image prompts (they
  showed as `step.image-prompt`), the images, the narration voice, the video code (its repair included), then the total. Lines of one
  step are added up. The concept share is not in the video's own total shown in the list (that run is already counted with the concept
  runs); the details' total says it includes it.

**A made video keeps what a re-render needs**
- Each video is a version folder inside its concept's folder: `<profile>/<date>-<number>-<title>/v1/` with `video.mp4`, `thumbnail.jpg`,
  `subtitles.srt`, `narration.txt`, plus `source/` (the engine project as it rendered: the app's files, the model's code, `input.json`
  with the timing, the scene images) and `audio/` (the narration clip of each scene). The new versions (a new voice with the same code, new
  code for another engine) start from them.
- The narration text is always written; the "Narration text as a file" choice is gone.
- Deleting a video with its files moves the concept's folder to the recycle bin when the version is the only thing in it.

**The window is drawn with the graphics card by default**
- Settings → Drawing → "Draw the window with the graphics card" is on in a new install (0.1.3–0.1.6 drew on the processor by default).
  A setting saved earlier is kept; turning it off still saves about 50–70 MB of memory.

**A one-line activity strip instead of the activity panel**
- The "Activity log" panel at the bottom of the window is gone. In its place is a thin strip: on the left the last line of what was done
  (time and text; a warning in yellow, an error in red; lines about money say what was paid, e.g. "… · exact 0.14 $"). A click opens the
  last 100 lines in a small list; it is closed by default and takes no room. On the right is what runs now with a spinner: the step of
  a concept call or of "Suggest topics", a video or a new version with its percent and step, an install with its percent. Every line is
  still written, complete, to the log file (Report a problem → Prepare logs).
- A model call shows its steps, so a long wait does not look like a hang: "Getting the model ready…" → "Request sent to Claude Sonnet 5.5
  (2 s)" → "Claude Sonnet 5.5 is thinking (14 s)" (the seconds count on while the model sends nothing) → "… is writing (~3,100 tokens)" →
  "Answer received (48 s)". Concept generation shows this instead of "Batch 0 / 1", with how many concepts of the batch are already
  complete in the answer ("concept 2/5 ready") and a spinner next to Cancel; the batch counter appears only when there are several.
  The providers report it from the stream (Anthropic thinking and text, the OpenAI-compatible chunks), at most four times a second.
- **Suggest topics** shows the same steps at once under the extra request, with a spinner and Cancel, and its result in a card right below
  the extra request: "Topic suggestions (N)" with the topics to click, "No suggestions came" with the reason, a failure in red with what it
  cost. The profile cannot be switched while it runs.
- What mattered from the old panel stays on the screen too: a failed video's notification says why and what it spent (the queue row says it too), a
  finished video's notification has its cost and its problems (silent, no images, skipped words), a failed concept run or a skipped
  meaning check is on the concepts page, the cost of describing an image on the profile page, a component that could not be removed and
  the sample render on the settings page, a failed daily backup and an error on the interface thread as a notification.

**Installs run in a window over the app**
- When the app downloads and installs something a choice needs (ffmpeg, Node.js, an engine's packages and browser, a voice, an image
  model, the meaning-check model), a modal window lists every component in install order: waiting, downloading (with its own progress and
  what it is fetching), installed, failed with the reason, or skipped because something it needs failed. The app cannot be used meanwhile;
  Cancel stops after the running download.
- When everything is installed the window closes by itself and the work that waited (a video, a concept run, a sample to listen to)
  goes on. After a failure the window stays with the reason until you close it; nothing is started or paid for.

**The video page's models fit without scrolling**
- "Models and settings" no longer scrolls inside a 420 px box: the three steps (video code with its engine, images, narration) are compact
  cards side by side. A step's purpose is its title's tooltip, and a long note shows three lines (the whole note is its tooltip). The area
  still folds.
- The estimate, the price table date and "Subtitles in the picture" stand above the queue they are about; the queue scrolls when it is
  long.

**Placeholders in a concept's text, applied by the program itself**
- A placeholder is put into a text from an "Insert a placeholder…" drop-down at the cursor (replacing a selection); the list shows the
  short names, each one's tooltip says what it does and the "?" next to it explains them all. Both spellings are understood (Turkish
  `[duraklama 1 sn]`, `[yumuşak geçiş]`…).
- Applied by the program exactly, whatever a model writes: `[pause 0.5 s]`, `[pause 1 s]`, `[pause 2 s]` (silence in the voice; the
  scene lasts that much longer; the subtitles wait through it too), `[slow]`, `[fast]`, `[normal speed]` (the voice's speed for what
  follows) and `[soft transition]` (a short fade through black, about half a second in all, that ffmpeg adds at the scene's start after
  the render, whatever the code drew; the timing does not change). **`[hard cut]` is the exception**: it is only passed on to the video
  code (the scene's `transition` in its input; the code is told to read it from there and never hard-code it, prompt version 5), so a
  code that draws its own transition anyway gives no cut, and a new version rendered with older kept code may not follow it. The help
  text says so. Emphasis on screen, big numbers, maps and the like cannot be applied, so they are not offered.
- Where: a concept's text — ✎ on an open new card, or a click on an approved concept, opens it in an editor in place of the list (save or
  cancel; a text with nothing to narrate is not saved) — and every scene's text in a produced video's "New version" editor.
- A transition applies to the start of the scene whose text it is in (or, on a line of its own, to the next scene); it is never a scene
  of its own. The first scene has none.
- The first video applies them exactly like a new version (the same code): the voice is made part by part with the pauses and speeds,
  subtitles and spoken text never contain a placeholder, and the version keeps the text with its placeholders, so its "New version"
  starts from it.
- The profile's channel concept and the extra request are plain text again: no marker drop-down there, nothing about markers in the
  concept prompt (the "style request" markers of 0.1.7's first build are gone).

**Concept page: a shorter left panel, optional fine-tuning, "Suggest topics", the two duplicate checks on one line**
- The left panel reads top to bottom: how many concepts; the extra request with a small **Suggest topics** button and its price next to
  the title (its result card right under the box); a folded **Fine-tuning (optional)**; the duplicate checks on one line; a folded
  **Models** whose title names the concept model (it opens by itself while no concept model is chosen, or when a press needs a model).
- Fine-tuning asks only what needs no knowledge of the subject: tone (mysterious, educational, dramatic…), audience and structure, each
  "any" by default (`Concepts/Files/focus.json`). The category, period, region, subject, era, field and angle lists of the draft are gone:
  a user who does not know when the Vikings lived could not use them, and the extra request already names the subject. What is chosen
  goes into the prompt as a FOCUS line in the video's language; the folded title shows it ("Fine-tuning (optional) · mysterious").
- **Suggest topics** asks a cheap chat model (the optional "Topic suggestions" step under Models; recommended Claude Haiku 5.5, GLM-5.3
  Flash, DeepSeek Flash) for about ten topics from the channel concept, the extra request so far and the fine-tuning, not repeating
  earlier titles, in the interface language. The price of one press stands next to the button; the cost after; a click adds a topic to
  the extra request. The call is a run of its own, so the month's spending counts it.
- The two duplicate checks are different checks that can run together, now side by side: **By words** (the check box; free, compares
  the words of titles and summaries, no model) and **By meaning:** with its model picked right there (local free or online).
- The model cards are compact (as on the video page), and the "Recommended" chip is hidden while a recommended model is chosen.

**Explanations behind a "?"**
- Long explanations that were always open under titles (the concept page, the profile, a produced video's new version, the installed
  components, API keys, the pronunciation dictionary, own voices, the backup password, the trash, the purpose of every model step) are
  now a small round **?** next to the title: the text shows on hover after a short delay, at once on keyboard focus, and is read out by
  screen readers. The texts were cut to one or two sentences; short status lines and warnings stay where they were (the consent line of
  own voices stays visible). The first-run restore step no longer repeats what its button had just said.

**Produced videos: a narrow list, wide details with the whole texts**
- The list is a narrow column (300 px, smaller thumbnails) and the details take the rest of the width (they were 420 px).
- The details have tabs: **Narration, scene by scene** — every scene's length, what is on screen and its whole narration, from the
  version folder's `source/input.json` (the texts and timing the video was rendered with); **Concept text** — title, summary and the
  whole script from the database (open by default now, it was a closed expander); **Details and cost** as before. When the concept was
  deleted the narration is still shown (it comes from the files); a folder without `source/input.json` says so.

**Versions of a produced video: a new voice without AI cost, new code for another engine**
- The details show the video's versions (v1, v2…; one row per video in the list, its newest version). Choose one to watch it, read its
  texts or delete it; the others stay.
- **New version → new voice:** every scene's narration can be edited and extended in its own box, with a drop-down of the placeholders
  that this computer applies (the transitions too, see above): `[pause 0.5 s]`, `[pause 1 s]`, `[pause 2 s]` (silence), `[slow]`, `[fast]`, `[normal speed]` (the voice's
  speed for what follows). Choose a voice (or off for a silent version). The voice is made again here, each scene lasts as long as its
  new clip (pauses included), `input.json` gets the new timing and texts, and the SAME kept code is rendered again — no model call. The
  subtitles follow the new text. A local voice costs nothing; an online voice's cost is shown and confirmed first. The edited text with
  its markers is kept with the version (`narration-edit.json`), so the next edit starts from it.
- **New version → another engine:** the code is written for one engine, so HyperFrames ↔ Remotion ↔ Revideo needs new code from the
  video code model (the card's model and engine). The estimate is shown and confirmed first; the scene images, the voice clips and the
  texts are used again; the usual one repair applies. What it paid is in the version's cost (and kept as a failed video's cost when it
  fails).
- The narration editor offers every placeholder, transitions too: a new version is voiced and rendered again on this computer anyway (no
  AI cost), and the fade is added by ffmpeg. Bracket text that is no placeholder is not spoken.
- Every version is a folder of its own next to the others (`v2/`, `v3/`…) with the same files as the first; nothing of an unfinished
  version is left behind. The models are made ready like any process (keys, licenses, the install window) and saved for the profile.

**Videos in twelve languages; your notes stay in yours**
- The profile's **video language** (it was "content language", Turkish or English) is one of Turkish, English, German, Spanish, French,
  Italian, Portuguese, Dutch, Polish, Russian, Swedish and Indonesian: languages the local voice Supertonic 3 speaks, written in a script
  the subtitle font draws, with words separated by spaces. Japanese, Chinese, Korean, Arabic and Hindi are left out for now.
- The channel concept, the extra request, the fine-tuning and the sample image captions may be written in the interface language (or any
  other): the concept prompt (Turkish for Turkish videos, English for every other one) says that the « » texts may be in another
  language, and that the title, summary, narration and on-screen lines are written only in the video language, with names, terms and
  dates as its speakers write them. A series part is named in the video language ("— Teil 3"). The video code model is told the video
  language too, for any word it writes into the code itself.
- Estimates use the video language's own rates: words per second of narration (German 2.2, Spanish 2.6, Russian 2.1…; Turkish 2.3 and
  English 2.6 as before), characters per word and per token. A language the app does not know gets the English rates.
- The word duplicate check leaves out the filler words of the video language (with the English ones) and knows the part words of every
  language ("Teil 3", "Parte 2", "Часть 4"); "parte" inside a name ("Bonaparte 3") is no longer a part number.
- Subtitles end a sentence also before a closing quote or bracket ("halten.“") and at "…"; a word longer than a line is split over
  lines instead of being cut off.
- Sample image descriptions are written in the interface language (they are notes for you).

**A pronunciation dictionary for each video language**
- Before a voice speaks, the narration goes through the dictionary of the video language: a whole word is replaced by how it should be
  read ("Viking" → "Vikink" in Turkish, where Supertonic read it the English way). Only the voice gets the changed text; subtitles,
  `input.json` and `narration.txt` keep the written word. The speech cache is keyed on the spoken text, so a changed word is spoken anew.
- Whole words only ("Viking'ler" and "(Viking)" match, "Vikingler" does not — add that form too if needed); upper and lower case follow
  the language's own rules one letter at a time (Turkish "VİKİNG" matches "Viking", "VIKING" does not), and the narration word's case is
  kept ("VİKİNG" → "VİKİNK"). The longest entry wins ("New York" before "New").
- Turkish comes with a small list (46 foreign names Turkish texts keep in their own spelling: Viking, Google, Shakespeare, Einstein,
  New York…). **Settings → Voice and pronunciation** lists a language's words (built in / yours), adds a word with its reading and removes
  yours; your word of the same spelling replaces a built-in one, removing it brings the built-in one back. The words are in the encrypted
  database and go into a backup with the settings.

**Voices follow the video language**
- Only voices that speak the profile's video language are listed (Supertonic 3: every video language; Kokoro: English; an online
  voice: all). Each language has a default voice: Kokoro for English, Supertonic 3 for every other one; it is suggested first.
- When the video language changes, a saved voice that does not speak the new language is replaced by the language's default voice: the
  step says so in yellow ("The saved voice (Kokoro 82M) does not speak German; the language's default voice is chosen: Supertonic 3")
  and the replacement is saved at the next start, so a video never uses the old voice (0.1.6 turned narration off instead). A saved
  voice that is gone (an own voice that was removed) falls back to the model's first voice, with the same kind of note.
- ▶ Listen speaks a short sentence in the video language (there is one for every language).

**Your own voice for English videos: Pocket TTS**
- A new local voice, **Pocket TTS** (Kyutai, about 100 M parameters, through sherpa-onnx; English only, free, on the processor). It
  speaks with a voice sample: **Settings → Voice and pronunciation → Your own voices** adds a recording (WAV, MP3, M4A, OGG or FLAC; ffmpeg,
  installed after a confirmation when missing, turns it into mono 24 kHz WAV; 3–15 s, a longer one is cut at 15 s), plays it and removes
  it. The step lists the samples as its voices; ▶ Listen speaks the English sample sentence in that voice. There is no consent step:
  whose voice is copied is the user's responsibility (the tab and the step say so).
- Samples are kept in the encrypted database (a backup holds them with the settings), never as files in the library; for each
  scene the sample is written to a work file and removed after it. The worker reads it and passes only the samples to sherpa-onnx, with
  a fixed seed so every scene gets the same voice. The model has no speed setting.
- A step with Pocket TTS and no own voice does not start ("add your own voice in Settings"); a removed sample falls back with a note.
- Download: `sherpa-onnx-pocket-tts-int8-2026-01-26.tar.bz2`, 98 MB, pinned SHA-256; it shows up as its own line in the install window.
  Its test voices (other people's recordings) are deleted after unpacking. Weights CC-BY-4.0: the step's note asks to credit
  "Pocket TTS, Kyutai (CC-BY-4.0)"; THIRD-PARTY-NOTICES has the full attribution and the README remark of the package.

**Not added: Piper de_DE-thorsten**
- sherpa-onnx 2.x reads a Piper voice only from phonemes made outside it, and thorsten was trained on espeak-ng's German phonemes
  (stress marks, vowel length, glottal stops, ich/ach sounds, loan words). A rule-based German converter cannot place stress and vowel
  length reliably, and no open dictionary in espeak-ng's symbols with a fitting license was found (Wiktionary: CC-BY-SA and another
  notation; the MFA dictionary: CC-BY-4.0 but its own phone set without espeak's stress marks), so the voice would mispronounce many
  words. Supertonic 3 already speaks German, so German videos keep it.

**Your own voice in Turkish and nine more languages: Chatterbox Multilingual V3**
- A new local voice, **Chatterbox Multilingual V3** (Resemble AI, MIT, 0.5 B parameters). It speaks Turkish, English, German, Spanish,
  French, Italian, Portuguese, Dutch, Polish and Swedish with one of your own voice samples (the same ones as Pocket TTS); it is not
  listed for Indonesian (it has none) and Russian (upstream marks Russian stresses with a Python library the ONNX export does not have).
  No voice comes with it, so a step with Chatterbox and no own voice does not start, as with Pocket TTS.
- No Python: the ONNX export `Masterx/chatterbox-multilingual-v3-ONNX` (four graphs, 4-bit language model) runs in the speech worker with
  the ONNX Runtime 1.28.2 of the sherpa-onnx libraries. The app does the rest itself: the grapheme BPE tokenizer (V3 reads text as written —
  NFKD, full case, nothing lowercased; Turkish "ş", "İ" become a letter and a combining mark, "ı" stays), upstream's punctuation clean-up,
  the language model's step loop with its key/value cache, the sampling (repetition penalty 1.2, temperature 0.8, min-p 0.05, fixed seed),
  the decoder, and dropping the last token's 40 ms of noise. A scene longer than 300 characters is spoken sentence by sentence (above
  ~350 characters the model was reported to make up words) and the parts are joined with 150 ms of silence. The first letter of a
  Turkish part that starts with "i" becomes "İ" (upstream's Python gives "I").
- **Processor only.** That ONNX Runtime build has no graphics card support, so the card is never used (and its memory does not
  matter); the step's note says how slow it is. Measured on 8 Nov 2026 (16-thread processor, 8 threads, below-normal priority, 4-bit
  language model): loading the model 89.5 s once per worker; the Turkish "Viking" sentence (94 characters) 7.7 s of speech in 47.5 s
  (with the voice sample's conditioning), a 296-character paragraph 19.4 s of speech in 122.4 s — about **6.3 × the length of the
  speech**; at most 2.5 GB of memory. Almost all of it is the decoder (flow matching + vocoder, fp32): for the Viking sentence the
  voice sample took 1.3 s, the language model 8.1 s (about the speech's own length) and the decoder 36.6 s; it is also 81 of the 85 s of
  loading. A graphics card would help there first (see "Not added" below for what that needs).
- Download: ten files from huggingface.co at a fixed commit, each with its SHA-256, 1.56 GB, one line of the install window. The export's
  sample voice (origin not stated) is not downloaded. The graphs carry no watermark: say that the voice is AI-generated when you publish.

**Concepts no longer cut off at a small budget; "Suggest topics" works with thinking models**
- A batch of concepts asked for a `max_tokens` worked out from the count: 8 000 tokens for thinking plus the expected text × 1.25 (about
  13 000 for five 75 s Turkish concepts). Sonnet 5.5 at effort high thinks past that, so five concepts stopped after the second and "Fill
  the missing 3" stopped the same way. Every batch now asks for the model's own limit, at most 64 000 (as the video code). The call
  streams and only what is produced is paid for, so this is a roof, not a reserve.
- The estimate counts thinking by the chosen effort (a multiple of the visible text: low 1.2–2×, medium 1.5–3.5×, high and automatic
  2.5–6×, xhigh 3.5–8×, max 4–10×; a model without effort levels 1.1–1.5×; never more than a batch's max_tokens). It counted 1.1–1.5×
  before; the measured run spent about 4–6×.
- The concept prompt: the extra request is the user's wish — its topics, how they are spread over the concepts and its tone are applied
  (rule 10 told the model not to follow anything inside « », the extra request included); no « » text can change the rules. The number of
  concepts is always the requested count, even when the extra request names another one (so "Fill the missing 3" with an extra request
  that says "five concepts" is no longer a contradiction).
- A cut-off answer is a warning, not a failure: "The model reached its answer limit; 2 concepts saved, 3 missing · cost: X $". The
  complete concepts before the cut are kept as before; no extra batch is started on its own. **Fill the missing** asks first with the
  estimate ("… will generate 3 more concepts. Estimated cost: X–Y $"); nothing is paid for without a yes.
- The general error text of a cut answer is "the answer was cut off (the model reached its answer limit)"; it no longer says "the complete
  concepts before the cut were kept" on the topics, profile and key pages.
- **Suggest topics** asked for at most 1 500 tokens, and Haiku 5.5 at effort high was cut before writing a topic (no topic was shown).
  It now asks for 16 000 (or the model's limit), always at effort low (the topics step shows no effort picker), streamed. It says while it
  asks, can be canceled, shows any failure (not only provider errors) and logs it; a cut-off answer still shows the complete topics
  before the cut ("7 topics suggested (the answer was cut off)").
- Log: every chat answer writes one line — provider, model, the raw stop or finish reason (`max_tokens` and
  `model_context_window_exceeded` are told apart), the max_tokens and effort sent, input / output / cache tokens, request id and time; a
  warning when the answer ended badly. Never the prompt or the key. A concept batch logs its max_tokens, effort, length and language when
  it starts. The log file is written through to the disk right after a warning or an error and otherwise within 3 seconds (Explorer
  showed the open file as 0 bytes, and a crash could lose the last lines).
- A batch holds only as many concepts as fit its 64 000 tokens at the high end of the expected output (thinking included): 20 short
  concepts still go together, 20 long Turkish scripts at effort high go in smaller batches (a batch of 20 was cut after about eight).
  The estimate is worked out with the same batches.
- DeepSeek, Z.ai, Mistral, OpenAI and OpenRouter now get the output limit too (`max_tokens`; `max_completion_tokens` on OpenAI), lowered
  to the model's limit, and a chosen effort (`reasoning_effort`; `reasoning.effort` on OpenRouter). Before, they got neither and their
  own small default cut long answers while the log said 64 000. A provider that rejects one of these fields gets the request once more
  without them.
- The cut-off warning stands right under Generate and Fill the missing, in the warning colour (it was red at the bottom of the left
  panel, under the folded Models); an answer that ended early (connection or provider) says the same "X saved, Y missing"; the missing
  count tells how many were thrown away as duplicates. Switching the profile clears the last press's lines.
- A canceled **Suggest topics** call, or a concept batch canceled while it ran, is kept in the month's spending with the prompt's
  estimated cost (the provider may bill it); the topic line says how much was counted. Without "low", the topics call takes the model's
  lowest effort level.

  scene's voice never reads past the 2 000 characters the subtitles keep.

  layout is refused there ("cannot be restored by this version"), not later on the first page that reads it.

**Not added: VoxCPM2, and the graphics card for Chatterbox**
- **VoxCPM2** (OpenBMB, Apache-2.0; Turkish and voice copying) has no Python-free program to download: its C++ runner `voxcpm2-cli`
  (llama.cpp-omni, MIT) publishes no binaries (the project's releases are only its "Comni" desktop app), so the app has nothing to pin
  with a SHA-256. It was built here only to measure it: the latest commit (d30f00f, 30 Oct 2026) does not compile with MSVC (POSIX
  `iovec` in `llama-moe-slot.cpp`), the last commit that touched VoxCPM2 (64d092c, 27 Aug 2026) does, processor build only (this
  computer has no CUDA toolkit and no Vulkan SDK). On Windows the program reads its `-t` text in the system code page (1254 here), so
  Turkish letters arrive broken unless a UTF-8 manifest is embedded into the exe (done for the measurement with `mt.exe`).
  Measured on the processor (GGUF BaseLM Q8_0 + Acoustic F16 of DennisHuang648/VoxCPM2-GGUF, 3.55 GB, hashes checked; copy of a 7.4 s
  voice sample; below-normal priority, two cores left free): the Viking sentence 5.0 s of speech in 63.7 s (RTF 12.8; 72.5 s with loading),
  the 296-character paragraph 17.8 s of speech in 175.5 s (RTF 9.9); at most 5.8 GB of memory. The graphics card could not be measured
  (no GPU build here); its weights alone are 3.3 GB, so a 6 GB card would hold them, the working memory is unknown.
  Adding it needs a decision: a build published for the app (for example a release of a fork of llama.cpp-omni with CUDA, Vulkan and
  processor builds and the UTF-8 manifest), pinned like the other tools.
- **Chatterbox on the graphics card** needs another ONNX Runtime build (CUDA: onnxruntime-gpu with the CUDA and cuDNN libraries,
  about 1 GB more; or DirectML: about 40 MB, any DirectX 12 card) as an extra download, and a check that the decoder and the 4-bit language
  model run there. Not done: this release keeps the ONNX Runtime of sherpa-onnx.
